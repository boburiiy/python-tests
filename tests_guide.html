1. Why write tests?

A test is code that calls your code and checks an expected result. Instead of manually trying the same inputs after every change, you save those checks and rerun them whenever you need to.

  • Catch regressions: a change that breaks behavior that used to work.
  • Clarify intent: a test shows what a function promises for ordinary and unusual inputs.
  • Make refactoring safer: if the tests still pass, you have evidence that important behavior stayed intact.
  • Find bugs sooner: a small failing example is easier to understand than a failure deep in an application.

Tests do not prove that a program has no bugs. They check selected behavior. The skill is choosing cases that represent the promises your code makes.

Useful question: “If this behavior broke tomorrow, what input would reveal it, and what result should I expect?” That question often gives you the next test.

2. Your first test

We’ll use pytest, a popular Python test runner. Install it once in your project’s virtual environment:

python -m pip install pytest

Imagine this production code lives in shop.py:

# shop.py
def total_with_tax(price, tax_rate):
    return round(price * (1 + tax_rate), 2)

Create test_shop.py beside it:

# test_shop.py
from shop import total_with_tax


def test_total_with_tax_adds_tax():
    result = total_with_tax(10.00, 0.10)

    assert result == 11.00

Run it from the project directory:

python -m pytest

Pytest discovers files named test_*.py or *_test.py, and functions whose names start with test_. A passing test is reported as a dot; a failure includes the assertion and useful context.

A good default structure is Arrange, Act, Assert:

  1. Arrange: prepare inputs and any objects needed.
  2. Act: call the function or operation under test.
  3. Assert: check the observable result.

Keep one test focused on one behavior. Clear names such as test_total_with_tax_rounds_to_cents make failures easier to understand.

3. Assertions and failures

An assert statement says that a condition must be true. If it is false, pytest reports a failure and shows the compared values.

assert total_with_tax(10.00, 0.10) == 11.00
assert "python" in ["python", "pytest"]
assert {"name": "Ada"} == {"name": "Ada"}

Check outcomes a user or caller can observe: returned values, raised exceptions, changed state, or output written to a file. Avoid checking private implementation details such as the number of internal helper calls unless that interaction itself is part of the contract.

For floating-point calculations, binary representation can make exact decimal equality surprising. Use pytest’s approximate comparison when the expected value is a calculated float:

import pytest


def test_average():
    assert (0.1 + 0.2) == pytest.approx(0.3)

For currency, integer cents or decimal.Decimal may be more appropriate than floats. Testing should reflect the representation your program is meant to use.

4. Choosing useful cases

For each behavior, consider more than the happy path. A practical checklist:

Kind of caseExample question
Typical inputDoes the common valid input produce the expected result?
BoundaryWhat happens at zero, an exact limit, or an empty collection?
Just outside boundaryWhat happens one step below or above the limit?
Invalid inputDoes the code reject it clearly, or handle it by documented design?
CombinationDo options still work correctly when used together?

Suppose a discount function should reject negative prices and discounts outside 0–100 percent. A few tests might be:

import pytest
from shop import discounted_price


def test_discount_reduces_price():
    assert discounted_price(100, 25) == 75


def test_zero_discount_keeps_price():
    assert discounted_price(100, 0) == 100


@pytest.mark.parametrize("price, discount", [
    (-1, 10),
    (100, -1),
    (100, 101),
])
def test_invalid_discount_inputs_are_rejected(price, discount):
    with pytest.raises(ValueError):
        discounted_price(price, discount)

Do not test every possible input. Pick cases that cover distinct rules, boundaries, and likely failure points. Tests should be small enough that a failure points you toward its cause.

5. Testing errors and exceptions

If invalid input is supposed to raise an exception, test that explicitly with pytest.raises. The code that should fail belongs inside the with block:

import pytest
from shop import total_with_tax


def test_negative_tax_rate_is_rejected():
    with pytest.raises(ValueError, match="tax rate"):
        total_with_tax(10, -0.5)

The match argument checks that the exception message contains a regular-expression match. Use it when the message is meaningful to callers; avoid tying tests to wording that is likely to change without changing the contract.

Choose the narrowest sensible exception type. A test that expects Exception could pass because of an unrelated bug, such as a typo causing NameError.

6. Fixtures and setup

A fixture provides setup that tests can reuse. It is useful when several tests need the same meaningful object or preparation—not just to avoid every repeated line.

import pytest


@pytest.fixture
def sample_cart():
    return {"tea": 2, "bread": 1}


def test_cart_has_two_teas(sample_cart):
    assert sample_cart["tea"] == 2


def test_cart_has_bread(sample_cart):
    assert "bread" in sample_cart

Pytest creates the fixture when a test requests it by name. By default, each test gets a fresh fixture result. This isolation is helpful: one test changing its cart should not affect another test.

Fixtures can also manage resources. Code after yield runs as cleanup:

@pytest.fixture
def open_resource():
    resource = acquire_resource()
    yield resource
    resource.close()

Prefer fixtures with clear, limited responsibilities. An overly large fixture can hide what a test needs and make failures harder to diagnose.

7. Testing many inputs

When the same rule should hold for several input/output pairs, use pytest.mark.parametrize. It runs the test once per row while keeping each case visible in the report.

import pytest
from shop import total_with_tax


@pytest.mark.parametrize("price, rate, expected", [
    (10, 0, 10),
    (10, 0.1, 11),
    (1.25, 0.2, 1.5),
])
def test_total_with_tax(price, rate, expected):
    assert total_with_tax(price, rate) == expected

Use parameterization for variations of the same behavior. Use separate tests when the cases express different rules or need different setup; readability matters more than reducing the line count.

8. Testing files and temporary data

For code that reads or writes files, pytest’s built-in tmp_path fixture gives each test its own temporary directory. Tests can use real file operations without touching important project files.

import json
from shop import save_receipt


def test_save_receipt_writes_json(tmp_path):
    output_file = tmp_path / "receipt.json"

    save_receipt(output_file, {"total": 12.5})

    saved_data = json.loads(output_file.read_text())
    assert saved_data == {"total": 12.5}

This checks the useful result—the file’s contents—rather than merely checking that a particular internal write method was called.

9. Mocks: when and why

A mock is a controllable stand-in for a dependency. Mocks are useful when a test would otherwise depend on a slow, costly, unreliable, or externally managed service—for example, an email provider or payment API.

Keep most tests focused on real behavior and use mocks at boundaries. Do not mock every helper: tests that copy the implementation’s internal call structure can fail during harmless refactoring.

Example: inject the email-sending function so the test can observe the notification without sending a real email:

def register_user(email, send_email):
    # Save the user, then notify them.
    send_email(email, "Welcome!")


def test_register_user_sends_welcome_message():
    sent = []

    def fake_send_email(address, message):
        sent.append((address, message))

    register_user("ada@example.com", fake_send_email)

    assert sent == [("ada@example.com", "Welcome!")]

For an existing module that calls a dependency directly, pytest’s monkeypatch fixture can replace that dependency for the duration of a test. Patch the name where the code under test looks it up, and restore behavior automatically by using the fixture.

Be careful: a mocked test proves how your code behaves with the mock, not that the real external service works. Keep integrations isolated and test them separately where practical.

10. A reliable testing workflow

  1. Write or identify a small piece of behavior with a clear expected result.
  2. Write a test that describes that behavior.
  3. Run it and check that it fails for the reason you expect. A test that never fails may not be checking what you think.
  4. Implement or change the code.
  5. Run the test again, then run the broader suite.
  6. If a bug escaped, add a test that reproduces it before fixing it. Keep the test as protection against the same regression.

This is often called red, green, refactor: see the relevant test fail, make it pass, then improve the design while tests stay green.

Handy commands:

# Run all discovered tests
python -m pytest

# Run one file or one test by name
python -m pytest tests/test_shop.py
python -m pytest -k "discount"

# Stop at the first failure and show more detail
python -m pytest -x -vv

# Measure which lines ran (install pytest-cov separately)
python -m pytest --cov=shop

Use python -m pytest to run pytest through the Python interpreter in your active environment. Coverage can show unexecuted lines, but high coverage is not the same as good tests: a line can run without its result being checked.

11. Common traps

  • Testing only the happy path. Add the boundaries and error cases that matter to the function’s contract.
  • Assertions that prove nothing. assert result only checks truthiness; prefer a specific expected value when possible.
  • Tests that depend on each other. Each test should set up its own state and pass when run alone.
  • Shared mutable state. Avoid one global list or database record that tests change without resetting.
  • Overly broad exception checks. Expect the intended exception type, not any exception.
  • Over-mocking. If a test asserts every internal call, small implementation changes can break it even while behavior remains correct.
  • Huge tests. A failure should make it reasonably clear which behavior is wrong.
  • Testing private details unnecessarily. Prefer stable, observable behavior over implementation trivia.
  • Trusting a green test without checking it. Temporarily break the behavior or use a known wrong expectation to confirm that the test fails, then restore it.

12. Practice exercise

Write tests for this function. Do not change the function while you are writing the tests:

def shipping_cost(subtotal):
    if subtotal < 0:
        raise ValueError("subtotal cannot be negative")
    if subtotal >= 50:
        return 0
    return 5

Think of a normal order, each side of the free-shipping boundary, and invalid input. A good set of tests would check:

  • a subtotal below 50 costs 5;
  • a subtotal exactly 50 costs 0;
  • a subtotal above 50 costs 0;
  • a negative subtotal raises ValueError.
Show one possible solution 
import pytest
from shop import shipping_cost


def test_shipping_cost_is_five_below_free_shipping_limit():
    assert shipping_cost(49.99) == 5


def test_shipping_is_free_at_limit():
    assert shipping_cost(50) == 0


def test_shipping_is_free_above_limit():
    assert shipping_cost(80) == 0


def test_negative_subtotal_is_rejected():
    with pytest.raises(ValueError, match="cannot be negative"):
        shipping_cost(-1)

Run these tests against the function. Then change one comparison—for example, change >= 50 to > 50—and rerun them. The exact-boundary test should catch the bug.

13. pytest and Python’s unittest

Python includes unittest in its standard library, so it does not need to be installed. It organizes tests as classes and methods:

import unittest
from shop import total_with_tax


class TotalWithTaxTests(unittest.TestCase):
    def test_adds_tax(self):
        self.assertEqual(total_with_tax(10, 0.1), 11)


if __name__ == "__main__":
    unittest.main()

Run a unittest file with python -m unittest. Pytest can also discover and run many unittest-style tests. Both are valid; pytest is used throughout this guide because its plain functions and readable assertions make a gentle starting point. Use the runner and conventions already adopted by your project when there is one.

Keep this mental model

A strong test says: given this meaningful situation, when I do this operation, I expect this observable result. Start with small tests for real promises, run them often, and let failures guide your next step.
